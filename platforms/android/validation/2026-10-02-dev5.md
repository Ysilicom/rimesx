## Layout and interaction

The reference is the read-only iOS main-working-tree snapshot inspected on
October 2: `StandardKeyboardGeometry.swift`, `KeyboardGeometry.swift`,
`KeyboardViewController.layoutRows` and `KeyboardTheme.swift`. Source hashes are
recorded in the JSON; this reference is independent of an iOS release.

| Geometry | Portrait | Landscape |
|---|---:|---:|
| Ordinary typing surface | 206 dp | 143 dp |
| Cap column / row gaps | 6 / 10 dp | 5 / 5 dp |
| Buffer panel, above candidates | 76 dp | 60 dp |
| Candidate / optional spelling row | 32 / 34 dp | 32 / 34 dp |
| Chord footer | 40 dp | 34 dp |

Android uses the iOS logical cap frames with separate contiguous touch cells,
5 dp outer padding and Android system insets. Buffer now occupies the two rows
above candidates. Ordinary Buffer has source/chips above statistics; plugin
mode has output above source. Send remains in the upper right, settings and the
plugin selector in the lower row, with Run beside the selector in plugin mode.
Long-press Send inserts all ordinary Buffer blocks. Confirmed words retain whole-block delivery; display
decoration never enters host text. Target retirement clears the model, drawing
cache and accessibility projection together.

The idle candidate row now contains the five iOS plugin shortcuts: **翻译、快问、
润色、作诗、画画**, each 68 × 30 dp with 6 dp spacing. It disappears during
composition or a held chord. Tap opens Buffer/selects a plugin; tapping the
active shortcut returns to ordinary Buffer. Long-press opens settings. Switching
plugins preserves source. The Android executors remain deferred: their output
and settings explicitly say the service is unavailable, and Send/Return never
insert unexecuted source as plugin output. Private/password targets have no entry.

Controls use **25 pinned official Lucide SVGs**, converted to Android native
VectorDrawable with round 2-unit strokes. Exact source/conversion hashes and the
complete ISC/MIT notice are checked at every build. No SF Symbols assets or
platform symbol fonts are embedded. Provenance is in
[icon lock](../resources/icons/lucide.lock.json) and
[icon conversion notes](../resources/icons/README.md).

QWERTY, nine-key Pinyin, numeric/symbol/emoji pages and 18 light/dark palettes
remain available. Normal/private Natural Code powers orthogonal and split
orthogonal touch chords. All **427** built-in mappings match the independently
executed iOS encoding fixture; nine directional slide routes are covered.
At most one finger participates per hand, endpoints can move, and only the last
finger's release resolves the batch. Extra/invalid contacts cancel it; retired
streams cannot acquire new contacts in another target.

These are geometry, color and Android rendering checks. Cross-platform font
rasterization, system chrome and animated assets differ; a full screenshot
pixel-diff pass is **not** claimed.

## Measured performance

Both UI runs use the same phone and real RIMES keyboard: **60 samples** per
metric after five warmups. The optimized run passes **787 assertions**.
Timings start at accessibility `ACTION_CLICK` submission and end at the actual
host EditText's TextWatcher mutation, including IPC and scheduling. They exclude
hardware touch detection and frame presentation.

| UI metric, ms | dev.4 mean / p50 / p95 / max | dev.5 mean / p50 / p95 / max |
|---|---:|---:|
| First composing key | 14.921 / 14.573 / **23.117** / 24.594 | 14.178 / 13.736 / **22.683** / 25.044 |
| First-candidate commit | 11.339 / 11.611 / **15.556** / 16.516 | 10.385 / 10.373 / **14.346** / 16.785 |

The final APK run shows p95 reductions of **1.88%** and **7.78%**. Earlier
dev.5 runs measured first-key p95 **18.436–24.039 ms** and candidate p95
**14.346–15.197 ms** across the five development/final runs. These variations
prevent a stable first-key speedup claim. Scheduling, caches and thermal state
vary; none of these measurements is hardware touch-to-display latency.
The final source also reuses immutable light/dark palettes, removing repeated
HSV/luminance calculation from keyboard and chord rendering.

The separate real-JNI benchmark was recorded on the earlier dev.5 snapshot
`6f4b932`, before the later UI/icon changes. Both packaged ABI libraries are
byte-identical through final `58f7395`, and the benchmark/worker/JNI engine source
is unchanged. It is same-engine reference evidence, not a final-APK rerun.
It uses isolated synthetic data and **private
schemas**, 20 warmup phrases and 200 measured phrases per schema. Counts are
1,000 Pinyin keys, 800 Natural Code keys, 400 Wubi keys and 1,000 nine-key keys;
each profile successfully commits 200 times. Full mean/p50/p95/max and session,
queue and memory metrics remain in the local benchmark JSON files.

| JNI key + immutable snapshot p95, ms | dev.4 | dev.5 |
|---|---:|---:|
| Pinyin | 0.103 | 0.073 |
| Natural Code | 0.322 | 0.234 |
| Wubi | 0.077 | 0.126 |
| Nine-key Pinyin | 0.220 | 0.234 |

Native timings move in both directions; no uniform engine acceleration is
claimed. Serial round trips additionally include worker submission and wakeup
of the instrumentation thread, not main-thread rendering or host delivery.
Learning-enabled latency is outside this benchmark.

Startup was sampled once per fresh target process with existing system
resources. Resource validation measured 58.974 / 33.340 ms, library load
7.172 / 3.051 ms and runtime initialization 0.080 / 0.076 ms. `ready_total`
69.230 / 37.125 ms covers that bootstrap only: librime loads schema components
and dictionaries lazily, with first session creation taking another
17.088 / 6.573 ms. This is not first-install extraction, keyboard readiness or
a stable cold-start distribution.

Buffer rendering now caches confirmed widths, draws only visible chips and
keeps coordinates within the viewport. The latest phone bitmap test passes
24 rendering checks and a synthetic **16,384-block** rail: the last measured
viewport draws 12 chips, confirmed glyph width is measured once, and 1,000
composition render/measure/draw iterations take **441.069 ms** without
remeasuring confirmed blocks. This software-draw test is not a hardware frame
distribution. Earlier failed viewport diagnostics remain in the evidence folder
and are excluded from the successful result.
